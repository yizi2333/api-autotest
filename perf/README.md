# 接口压测（JMeter）

> 用 **Apache JMeter 5.6.3** 对被测系统做接口压测。
> 计划文件：`api-load.jmx` ｜ 运行方式：**无头模式**（CI 友好）

## 为什么压测也要写断言

`api-load.jmx` 里每个采样器都挂了 **Response Assertion**。

> ★ 这是压测最常见的坑：**只压不断言**。
> 如果被测服务挂了、认证失效了，请求会快速返回 500 / 401 ——
> 响应时间反而**变短了**，TPS **变高了**，报告看起来"性能很好"。
> **没有断言的压测，测得越快越可疑。**

## 场景设计

| 采样器 | 说明 | 类型 |
|---|---|---|
| `01 POST 注册` | 每线程一次，用户名用 `${__threadNum}` + `${__time(,)}` 保证唯一 | 前置（Once Only） |
| `02 POST 登录` | 拿 token，用 **JSON 提取器** 存成变量 `${token}` | 前置（Once Only） |
| `03 GET 查询资料` | 带 `Authorization: Bearer ${token}`，**主压测目标** | 主力 |

**参数关联**是重点：登录响应里的 token 被 JSON 提取器抽出来，
自动注入后续所有请求的头 —— 这和 pytest 框架里 `client.set_token()` 是同一件事，
只是换了工具。**面试问你"JMeter 怎么做参数关联"，答案就是 JSON 提取器 + 变量引用。**

**负载**：10 线程 × 20 轮，ramp-up 2 秒。

## 运行方式

```powershell
# 起被测系统
uvicorn sut.app:app --port 8000

# 无头压测 + 生成 HTML 报告
jmeter -n -t perf/api-load.jmx -l perf/results.jtl -e -o perf/report

# 报告入口：perf/report/index.html
```

| 参数 | 含义 |
|---|---|
| `-n` | 无头模式（不启动 GUI，CI 里必须用这个） |
| `-t` | 测试计划文件 |
| `-l` | 结果明细（.jtl，CSV 格式） |
| `-e -o` | 生成 HTML 仪表盘报告到指定目录 |

## 实测结果（2026-10-12）

| 采样器 | 次数 | 平均 | P95 | 最小 | 最大 | 错误 |
|---|---:|---:|---:|---:|---:|---:|
| 01 POST 注册 | 10 | 58.6 ms | 107 ms | 19 ms | 114 ms | 0 |
| 02 POST 登录 | 10 | 30.2 ms | 45 ms | 11 ms | 71 ms | 0 |
| **03 GET 查询资料（带 token）** | **200** | **37.4 ms** | **79 ms** | 9 ms | 115 ms | 0 |

- **总采样 220 ｜ 墙钟时长 2.04 s ｜ 吞吐 108.1 req/s ｜ 失败请求 0**
- **错误率 0.00%** —— 断言全部通过，说明数据是可信的

## 怎么读这份报告

| 指标 | 含义 | 为什么重要 |
|---|---|---|
| **P95 / P99** | 95% / 99% 的请求快于该值 | 平均值会掩盖长尾。用户骂的永远是那 1% 的慢请求，不是平均值 |
| **吞吐（req/s）** | 单位时间处理的请求数 | 和响应时间一起看才是容量 |
| **错误率** | 非 2xx 的比例 | **必须先看这一列**。错误率高时，其他指标全都不可信 |
| **拐点** | 压力继续加、TPS 不再涨甚至下降 | 那才是系统瓶颈所在 |

> ⚠️ **这份数据的边界**：
> - 压的是**本机回环**（127.0.0.1），没有网络延迟
> - SQLite 单文件，没有连接池竞争
> - 10 并发在**本机 Python 单进程**上，**远没到瓶颈**
>
> 所以这份结果的价值是「**验证压测流程能跑通**」，
> **不是**「这台服务能扛 108 QPS」。面试时被追问，要主动说清这个边界 ——
> 把压测数据说成容量结论，是最容易被戳穿的一类夸大。
